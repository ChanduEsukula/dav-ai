## Installer and runtime audit

- **Integrity and identity:** `release_connection.py:173` seals 4,825,108,480 bytes and SHA-256 `87779eda6b06c75f10603762b18f8c66a5cb7b12ed37d47ab1bf9b4825639c71`. `:146` checks exactly one manifest, release ID `dav-ai-pharma-v1-phase4b-communications-20261006`, contract `dav-ai-pharma-release-v1`, policy `1.0.0`, user_version 4 and all 19 required tables. Build-version text is selected but not separately matched; the exact whole-file hash seals it and the complete schema. Receipt fields cannot substitute for hashing during install/activation. No environment variable changes these production constants.
- **Installation:** `artifact_store.py:168` opens the incoming source read-only, bounds and hashes the stream, makes an independent inode copy, fsyncs, and fully verifies the copy before publishing a version directory. Existing versions refuse overwrite; hidden pending directories are not selectable. Only the new copy is chmodded. Source-path symlinks are canonicalized intentionally; no source writing is performed. No installer HTTP route exists; the CLI is excluded from the API image.
- **Permissions and paths:** Version identifiers cannot contain separators or begin with dot; final root and managed releases/version/file/receipt/selection symlinks are refused. Databases are 0444 and installation directories 0555. These are permission-based immutability, not an immutable filesystem flag. Ancestor symlinks are canonicalized, not categorically rejected; the old source comment overstated that protection and is corrected. Ancestor ownership/ACLs/mount semantics are not automatically audited. Operators must validate canonical ancestry and prevent untrusted rename/write access. A read-only mount protects the runtime, not against a hostile host operator.
- **TOCTOU limits:** Hashing and SQLite opening remain separate path operations with before/after identity checks. The design does not withstand a hostile root/operator doing an ABA path swap or modifying an open immutable SQLite inode. Filesystem ownership is an explicit prerequisite. The metadata fix narrows a concrete race without pretending to replace that prerequisite. Advisory flock only coordinates cooperating tools; noncooperating privileged writers remain outside the guarantee.
- **Activation/concurrency:** `artifact_store.py:221` rehashes/verifies the target under flock before atomic JSON replacement. Concurrent valid A/B activation plus a failing target produced only A/B active/previous states. Idempotent activation retains the previous version. Pre-replace failures preserve the pointer; post-replace directory-fsync errors can leave a complete valid new pointer with uncertain crash durability. Inspect after any ambiguous error. No power-loss or target-filesystem durability test was performed.
- **Rollback/recovery:** Both use full verification before selection. A corrupt previous target cannot be promoted; failed recovery leaves corrupt selection unchanged, and explicit recovery of a valid retained target succeeds. Healthy selection cannot be overwritten using recovery mode. All supported installation labels currently contain copies of one exact release, not independently authorized different releases. This proves integrity-preserving selection, not a future multi-release approval protocol.
- **Pinning/cache:** `artifact_store.py:284` pins a selected path for process lifetime; activation takes effect on restart. `release_connection.py:179` caches checksum verification by device/inode/size/mtime/ctime. Changed bytes with restored mtime are rejected. Offline activation always bypasses the cache and rehashes. An existing pin intentionally ignores later selection/receipt changes; it is not an authorization-revocation channel. A future scoped approval must be evaluated separately and expire/revoke safely.
- **Source preservation:** Installation's source descriptor is O_RDONLY, copy inode differs, and tests preserve its signature. Cleanup removes only validated pending content; it refuses installed labels and unexpected entries. Operator-controlled roots must be separate from incoming/frozen release and evidence directories. The original frozen artifact was only read during this review and still has mode 0444 and its exact size/hash. Both original metadata copies remain `publication_validated=false`; see `verification/preservation.json` and `original-artifact.txt`.

## Shared gate, readiness and routes

`release_connection.py:69` denies hosted serving before opening SQLite. `main.py:51` requires startup verification for hosted modes or a managed root; failed authorization or missing/corrupt/inaccessible data refuses startup. With lifespan bypassed solely for diagnostic TestClient requests, `/ready` and data routes still fail closed. `/health`, `/`, and API documentation are liveness/schema surfaces, not release authorization or pharmaceutical data.

All registered data surfaces were traced through `connect_release`: search and identity, aggregate safety, labels/recalls/adverse_events/communications sections, timeline, shared evidence, coverage, and PDF generation. Tests deny each in production/staging/preview with a valid installed artifact. Invalid requests may receive validation/rate-limit errors before the data gate, but no data is returned. PDF rate limiting is not authentication. CORS and an exact origin are not access controls. No request header/query/body grants approval. Activation/receipt authorization fields cannot turn publication on; forged selection authorization values and incompatible receipts fail validation.

Hosted modes continue to deny even a correct artifact and regardless of an external metadata approval change. This review did not implement a publication-approval consumer. Public serving therefore remains closed until a separately reviewed mechanism exists; changing a JSON flag alone would not authorize deployment.
