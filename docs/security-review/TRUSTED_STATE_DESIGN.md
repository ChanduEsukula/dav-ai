## Trust boundaries and threat model

Untrusted inputs include approvals, signatures, revocation downloads, transport metadata, request headers/body/query, artifact pointers/receipts as serving authority, and replayed historical signed records. Attackers may mutate bytes, duplicate fields, choose IDs, replay or reorder records, cause outages, or restore an application/container/local-volume snapshot. A signer compromise is in scope for emergency revocation. Application snapshot rollback must not roll back the independent authorization control plane.

Trusted dependencies must include an independent authorization authority, authenticated policy provisioning, trusted UTC time, independently attested deployment/image/config identity, immutable artifact ownership, a linearizable durable state service with external rollback detection, and enforced private authenticated ingress. Host/root compromise and compromise of the independent root authority are not solved by these Python primitives. A caller able to replace Python policy/store objects already controls this boundary.

The artifact installer must not issue approvals, select trusted public keys, advance/reset trust checkpoints, or attest deployment identity. The app must never contain approval/revocation private keys. All tests generate ephemeral synthetic Ed25519 keys.

## Independent authority and public-key provisioning

An independently owned control plane must provision `TrustPolicy` over an authenticated channel. Pin authority identity, exact release ID/SHA256, private staging deployment identity, distinct Ed25519 public keys and validity/status. Policy mappings are copied and read-only; lifecycle entries are frozen. Aliases sharing the same public-key material within either registry are rejected, so a second ID cannot evade a key-ID tombstone. The code cannot prove where a supplied policy originated. Policy versioning, integrity, downgrade protection, refresh leases and audit ownership require external implementation before serving.

Approval and revocation keys must not share identifiers or public-key bytes across roles. Each policy represents one revocation authority and one deployment/release scope; do not reuse a global revocation store across authorities without authority partitioning. Within an authority, sequences continue across signing-key rotation, deployments and release rollback. Release rollback does not reset revocation state. The schema has no epoch-reset mechanism.

No document-provided public key, JWK URL, algorithm selector, environment override or trust-on-first-use fallback is accepted. Ed25519 is fixed by the provisioned key type. Verification signs/verifies the exact bounded UTF-8 payload bytes; no verifier-side JSON reserialization or ambiguous canonicalization occurs. A future issuer must publish a compatible exact-byte signing profile and reviewed transport/envelope; this phase does not invent one.

## Authenticated distribution and durable state

A future authenticated distributor obtains signed full revocation snapshots. TLS/client authentication, bounded downloads and caching are still required; transport freshness alone never renews signed validity. Authority/key identity, exact fields, signature, integer sequence (0 through 2^63-1), unique nonempty ID lists and signed timestamps are verified locally. Record lifetime is at most five minutes; approval lifetime is at most 24 hours. These are conservative offline ceilings, not an approved production freshness/availability SLA.

`accept_signed_revocation` reads a preexisting trusted checkpoint, verifies the new signed record with `sequence > previous.sequence`, enforces cumulative tombstones, and performs CAS on the **whole** checkpoint. The provider must authenticate reads and writes, enforce authorization, compare atomically, durably persist record bytes/signature/sequence/tombstones together, and acknowledge only after durable commit. Missing state never bootstraps automatically. Failed/ambiguous commits deny; reread independently trusted state to determine whether the commit occurred. A duplicate or equal-sequence conflicting record is rejected rather than refreshing expiry. Sequence gaps are allowed because snapshots are complete and cumulative. Exhaustion requires an independently reviewed migration, never wrapping/resetting the integer.

`validate_trusted_staging_decision` reads and re-verifies the stored signed bytes at the decision time, checks checkpoint metadata consistency, approval signature/scope/lifetime/key status and both revocation sets, and rereads the checkpoint before returning. It does not write on each decision. A trusted bootstrap checkpoint without signed current bytes cannot authorize anything. Revocation key IDs in `revoked_signing_key_ids` are **approval signer tombstones**, not permission to redefine the authority's own roots.

`StateStore` is a protocol, with **no production implementation or default local fallback**. Its `read` must fail when an independent witness detects restore/rollback; its CAS must not allow an app rollback to reset state. A locally stored counter, SQLite row, fsynced file, container volume, or local backup is not independently rollback-resistant. Signatures alone also cannot distinguish an older valid snapshot after its external high-water mark has been lost. The test fake simulates an external witness using a separate in-memory number; it is neither persistent nor independent. Its rollback tests prove the consumer's fail-closed handling and replay/CAS contract, not infrastructure durability.

## Anti-rollback recovery and availability

On missing checkpoint, detected rollback, invalid/expired signature, stale record, wrong scope, unavailable clock/policy/store or failed commit, deny. Restart, backup restore and volume replacement must never implicitly initialize sequence zero. Only an independently authenticated bootstrap/recovery procedure may seed the store from the latest authoritative sequence **and cumulative revocations**. A valid higher-sequence signed snapshot alone does not prove it is newer than lost historical state. Recovery must reconcile with an external retained witness/audit history, freeze serving during uncertainty, and produce an independent audit receipt.

A stale prior checkpoint may be advanced by a current, valid newer snapshot. No expired record is accepted for serving and no local fetched-at value extends validity. If an authority key is revoked by trusted policy, even an already cached record signed by it denies; a current replacement record signed by a new independently provisioned key must arrive with a higher sequence and cumulative tombstones. If no safe replacement exists, availability is sacrificed. Distribution retries must treat duplicate ingestion separately from reading the already accepted snapshot.

## Key rotation and emergency response

Provision new keys with explicit validity intervals before issuance; permit controlled overlap. A document's full interval must lie within its signing key interval (`not_before <= issued < expires <= not_after`), and the key must be active at evaluation (`not_before <= now < not_after`). The policy revoked flag immediately denies regardless of original issuance. IDs must never be reused with different material; independent provisioning must enforce that historical property (the static Python policy cannot).

For approval-key compromise, publish a current cumulative snapshot containing its ID and independently remove/revoke the key in policy. Existing cached snapshots may persist until the signed expiry ceiling, so the final refresh SLA and emergency invalidation path need review. For revocation-key compromise, replace/revoke the authority key via the independent policy root, not via a self-signed unrevocation or caller-provided registry. Rotation must preserve the authority sequence and all tombstones. Authority/root compromise requires a separately approved recovery plan; this phase has no automatic root replacement.

## Deployment binding, TOCTOU and enforcement

Policy binds release ID, SHA256 and deployment ID; approval claims must additionally say `environment=staging` and `audience=private`. Do not source expected deployment ID from request headers, caller fields, a mutable local environment string, or the approval itself. A future trusted identity provider must bind deployment ID to reviewed workload/image/config identity and prevent cloning/reuse. The current approval wire format does not carry separate image/config claims: these must be bound through that independently attested deployment identity or a versioned future schema.

An offline return value is not a reusable serving capability. The second state read only narrows a race; state/time can change after it. Future integration must specify the transaction/lease boundary for each data access, long-running query/PDF generation and in-flight work during revocation, including maximum revocation latency and rechecking expiry. Startup/readiness-only checks are insufficient. Policy updates require trusted refresh and bounded expiry too. No such runtime integration is included here.

The deployed-environment guard, `connect_release` denial, startup/readiness behavior, frozen database, publication flags, Vercel Authentication, Render Maintenance Mode, frontend design and staging infrastructure are untouched.

## Audit logging requirements

A future integration must emit structured, bounded events for policy installation/version changes, key lifecycle changes, checkpoint bootstrap/advance/conflict/replay/rollback, distribution outage/staleness, recovery, authorization acceptance/denial and independent operator review. Include trusted authority/deployment/policy identifiers, previous/new sequence, record digest, fixed reason code, trusted UTC time and correlation ID. Avoid raw documents/signatures, secrets, personal/report data, arbitrary request IDs and unbounded attacker strings. Retain tamper-evident logs outside the rollback domain with access control and monitored alerts for rollback, policy downgrade and revocation outage. Fail closed if the selected audit requirements cannot be met. These isolated helpers do not pretend local logs provide that facility; logging ownership, retention and audit availability policy remain to be implemented.

## Private staging acceptance and infrastructure decisions

Before any serving-gate change or deployment:

1. Independently review issuer ownership, offline root protection, policy provenance/downgrade protection, authority partitioning and key rotation/emergency drills.
2. Implement/qualify a durable linearizable store and independently retained high-water witness. Demonstrate restart, restore, container rollback, concurrency, outage, ambiguous commits and authenticated recovery on the actual provider.
3. Implement authenticated revocation distribution and approve refresh cadence, clock trust/drift, signed expiry limits, policy refresh SLA and incident response latency. Exercise stale/missing/tampered/replayed/equivocating records.
4. Attest workload identity, exact artifact/image/config and scope; prove request/header/env spoofing and cloned deployment identity cannot authorize serving.
5. Choose independently authenticated TLS ingress; protect all frontend, API, docs and operational paths, and prove direct backend/static-origin bypass fails. Keep Vercel Authentication and Render Maintenance Mode intact until separately authorized changes.
6. Design and test startup/readiness/every-data-access enforcement with explicit in-flight TOCTOU rules. Preserve public-production denial and `publication_validated=false`.
7. Qualify filesystem ancestry/ownership/storage semantics and real artifact integrity, provider durability, dependency/image scanning, browser journeys and operational audit/recovery acceptance.
8. Obtain independent security/engineering review and separate explicit deployment authorization. Isolated tests cannot satisfy these infrastructure acceptance criteria.

No signing service, identity provider, persistent state backend, ingress or deployment is created by this phase.
